# DataMaster ABTest 从零扫盲

> 面向完全没接触过 AB 测试的人。读完你应该能回答三个问题：
> **AB 测试到底在干嘛？客户端要配合做哪几步？最后靠什么判断谁赢了？**
> 全文尽量用大白话和例子，不涉及代码和变量。

---

## 一、先讲一个故事：AB 测试的本质

假设你是一家奶茶店老板，你在纠结一件事：

> **「买一杯」按钮做成红色好，还是做成绿色好？** 哪个能让更多人下单？

你有两种做法：

- **拍脑袋**：老板觉得红色喜庆，就全店都用红色。结果好不好，全凭感觉，说不清。
- **做实验**：进店的顾客，**一半人看到红色按钮，一半人看到绿色按钮**。一周后统计——看到红色的人里有 10% 下单，看到绿色的人里有 15% 下单。**结论：绿色赢，全店换绿色。**

第二种做法，就是 **AB 测试**。

**它的实质是一句话：把用户随机分成几组，每组给不同的方案，然后用真实数据来判断哪个方案更好，而不是靠猜。**

- 「A」和「B」就是两个（或多个）不同的方案。
- 「随机分组」是关键——两组人本身没差别，唯一的差别就是你给他们的方案不同，所以结果差异只能归因于方案本身。
- 「用数据判断」是核心——最后比的是转化率、留存、付费这些**能用数字衡量的结果**。

游戏里也是一样的问题，比如：

- 新手引导第一步，是**先送金币**还是**先打一关**，哪个留存高？
- 复活按钮定价 **80 钻** 还是 **100 钻**，哪个总收入高？
- 商城首页默认展示**礼包**还是**皮肤**，哪个付费率高？

这些「说不准、又很重要」的决策，就是 AB 测试要解决的。

## 二、AB 测试涉及三个角色

要把这个实验跑起来，需要三方配合。理解了这三方，你就理解了整个系统。

```
   ┌─────────────┐        ┌─────────────┐        ┌─────────────┐
   │  ① 后台管理台  │        │  ② 游戏客户端 │        │  ③ 数据分析端 │
   │  （策划操作）  │  ───▶  │  （SDK 干活）  │  ───▶  │  （看报表）   │
   │              │        │              │        │              │
   │ 定方案、分流量 │        │ 拉方案、按方案 │        │ 收数据、算谁赢 │
   │              │        │ 展示、报数据   │        │              │
   └─────────────┘        └─────────────┘        └─────────────┘
```

1. **后台管理台**（策划/运营用）：定义「要测什么功能」「有哪几个方案」「多少比例的人分到哪个方案」。就是那三张流程图里 `选择应用 → 创建主题 → 定义参数 → 发布` 干的事。
2. **游戏客户端**（你负责的部分，DataMaster SDK 在这里干活）：向服务器要「这个玩家该用哪个方案」，拿到后**按方案配置游戏表现**，并把玩家的行为**上报**回去。
3. **数据分析端**（数据/策划看）：把所有玩家的行为汇总，按分组算出「A 组转化率 vs B 组转化率」，得出结论。

**你作为客户端开发，只跟 ② 打交道，但要理解 ① 和 ③，才知道自己每一步是为了谁做的。**

## 三、几个核心词，用大白话翻译

后台和 SDK 里会反复出现几个词，先翻译成人话，后面就不懵了：

| 术语 | 大白话 | 奶茶店类比 |
|---|---|---|
| **主题 / Topic** | 你要测试的**一个功能点**（一个容器，装着这次实验的所有东西） | 「按钮颜色实验」这件事本身 |
| **参数 / Param** | 这个功能里**可以被远程调整的一个配置项** | 「按钮颜色」这个可调的设置 |
| **方案 / Case（实验分组）** | 同一个参数的**一种取值组合**，代表一组玩家会体验到的版本 | 方案A=红色，方案B=绿色 |
| **分桶 / 分流** | 服务器**决定这个玩家属于哪一组**的过程 | 门口迎宾把顾客分到红桌/绿桌 |
| **曝光 / Exposure** | 玩家**真正看到/接触到**这个实验功能的那一刻 | 顾客真的走到了点单台前，看到了按钮 |
| **事件 / Event** | 玩家做的**一个可统计的动作** | 顾客「下单了」这个动作 |
| **默认值 / 兜底配置** | 拿不到服务器方案时，**本地自带的一套安全配置** | 断网时店里挂的那块固定菜单 |

一句话把它们串起来：

> 后台针对一个 **主题**（某功能），设了几个 **参数**，每个参数在不同 **方案** 下取不同值；服务器给每个玩家 **分桶** 到某个方案；客户端按这个方案展示，在玩家 **曝光** 时打个标记，并把后续 **事件** 报回去，最后数据端比较各方案的转化。

## 四、客户端视角的完整时间线（先怎样，后怎样）

这是你最关心的部分。把一次游戏启动，从头到尾走一遍：

### 第 0 步（发版前，准备工作）
策划在后台把方案配好，**导出一份「默认配置」JSON**，随游戏包一起打进去。
> 作用：万一玩家断网、或服务器还没给这个玩家分方案，游戏也能用这套本地配置正常跑，不会白屏。

### 第 1 步（游戏启动）：先用默认配置把游戏跑起来
客户端加载那份随包的默认配置，让游戏**先用兜底的一套配置正常启动**。
> 关键点：**不要等网络**。先保证游戏能玩，方案是不是最新的，后面再说。

### 第 2 步（玩家登录后）：去服务器要「专属方案」
客户端带上**这个玩家的身份和属性**（玩家ID、设备、国家、版本、等级、是否VIP 等）去问服务器：
> 「这个玩家，各个实验该用哪个方案？」

服务器根据这些属性和分流规则，**算出这个玩家属于哪一组**，把对应的方案配置**下发**回来。

### 第 3 步：拿到新方案，替换掉默认配置
客户端收到服务器方案后**存到本地**，然后**通知各个业务模块**：「配置更新了，重新读一遍」。
> 这时候按钮颜色、复活价格等，才真正切换成这个玩家被分到的那一版。

### 第 4 步：玩家真正用到这个功能时，打「曝光」标记
当玩家**真的看到/进入了这个实验功能**（比如真的打开了商城、真的看到了那个按钮），客户端记一笔「曝光」。
> **这一步极其重要，下一节专门讲为什么。**

### 第 5 步：玩家做动作时，上报「事件」
玩家下单了、复活了、看广告了……客户端把这些动作**上报**给数据端。
> 这些就是最后用来算「谁赢」的原始数据。

### 第 6 步：读取配置贯穿始终
游戏任何地方需要用到某个配置（按钮什么颜色、价格多少），就**按主题+参数名去本地读当前生效值**。
> 读到的要么是服务器下发的方案值，要么是兜底的默认值。

**串起来的一句话时间线：**

> 启动 →（先用默认配置跑）→ 登录 →（问服务器要方案）→（换成新方案并重读）→（玩家用到功能时打曝光）→（玩家做动作时报事件）。

## 五、为什么「曝光」这么重要？（初学者最容易忽略的点）

回到奶茶店。假设你把 1000 个会员分成红组和绿组，各 500 人。一周后统计下单率——

**但问题来了**：这 500 个绿组会员里，有 300 个这周**根本没来过店**，压根没看到过绿色按钮。你如果拿「500 人里多少人下单」来算，就把 300 个没看到按钮的人也算进分母了，**结论完全被稀释、失真**。

正确做法是：**只统计「真正走进店、真正看到了按钮」的那些人**。看到红按钮的人有多少下单，看到绿按钮的人有多少下单——这才公平。

「曝光」标记，就是客户端在告诉数据端：

> **「这个玩家，从这一刻起，真正进入了这个实验的影响范围。」**

所以：
- **分组 ≠ 曝光**。玩家被分到某组，不代表他体验到了这个功能。
- 只有打了曝光的玩家，才会被计入实验的分母。
- 曝光一般**只打一次**（第一次接触时），之后重复接触不再重复标记。

**记住这条原则：曝光打错，整个实验数据就废了。** 曝光要打在「玩家真正接触到实验功能」的那个准确位置，不能太早（一登录就打，把没玩到的人算进来），也不能太晚（都下单了才打）。

## 六、最后怎么「比较」出谁赢？（AB 测试的判定原理）

数据端手里有两类数据：

1. **谁在哪一组**（分桶信息） + **谁被曝光了**（曝光标记）
2. **每个玩家做了哪些动作**（事件，比如「下单」「付费金额」）

比较的逻辑非常朴素，就是**分组算比率，然后比大小**：

```
A 组（看到红按钮的人）：曝光 4000 人，下单 400 人  → 转化率 10%
B 组（看到绿按钮的人）：曝光 4000 人，下单 600 人  → 转化率 15%

结论：B 组转化率明显更高 → 绿色方案胜出 → 全量推给所有人
```

几个要点：

- **比的是「比率」不是「绝对数」**：因为两组人数可能不完全相等，只有比率才公平。
- **指标由你定**：可以是转化率、次日留存、人均付费、广告观看次数……看这次实验想优化什么。这就是为什么客户端要上报事件——事件是算指标的原料。
- **需要足够样本量**：如果只有 10 个人，10% 和 15% 可能只是运气。人够多，差异才可信（这一步数据端会用统计方法判断「差异是不是真的，而不是巧合」，客户端不用管）。
- **随机分组是公平的前提**：因为两组人除了「看到的方案不同」以外没有系统性差别，所以转化率的差异**只能归因于方案本身**——这就是 AB 测试敢下结论的根本原因。

## 七、AB 测试的工作原理，一张图收尾

```
后台：把「按钮颜色实验」配好，A=红 B=绿，各分 50% 流量
              │
              ▼
玩家登录 ──▶ 客户端带玩家属性问服务器：「我该用哪个方案？」
              │
              ▼
服务器：根据玩家ID+属性，稳定地把他分到 A 或 B（同一玩家每次都分到同一组）
              │
              ▼
客户端：拿到方案 → 按方案展示（红 or 绿）→ 玩家看到时打「曝光」→ 玩家下单时报「事件」
              │
              ▼
数据端：把所有玩家按 A/B 分组，只看曝光过的人，算各组转化率，比出高低
              │
              ▼
结论：哪个方案转化率高，就把它作为「默认方案」全量上线
```

**核心原理再总结一次：**

> 1. **随机且稳定分组**：把用户分成对照组和实验组，同一个用户始终在同一组（这样体验不会跳变，数据也干净）。
> 2. **控制单一变量**：两组唯一的差别就是那个被测的方案，其他都一样。
> 3. **用数据说话**：收集真实行为，按组算指标，比出高低，用胜出方案替换拍脑袋决策。

## 八、这个 SDK（DataMaster）在里面扮演什么角色？

现在回头看这个 SDK 就清晰了——**它就是第四节客户端那几步的执行者**。你不用记具体函数名，只要知道它负责这几件事：

| 客户端要做的事 | DataMaster 帮你做 |
|---|---|
| 启动时用本地兜底配置 | 加载并解析随包的默认配置 |
| 登录后向服务器要方案 | 带玩家属性去拉取，服务器分桶后下发 |
| 把方案存下来、供全局读取 | 存本地数据库（还做了加密防篡改），提供「按主题+参数名读值」的接口 |
| 玩家真正接触功能时打曝光 | 提供一个「记录曝光时间」的接口给你在合适位置调用 |
| 上报玩家行为供数据端比较 | 提供事件上报接口 |
| 让同一玩家每次分到同一组 | 每次拉取时把本地已有的实验状态回传给服务器，保证分组稳定 |

**它额外还顺手做了两件事**（了解即可）：本地存储加密（防止玩家改本地配置作弊）、请求压缩加密（省流量+安全）。

## 九、你现在该有的心智模型（一句话版）

> **AB 测试 = 把玩家随机分组、每组给不同配置、用真实数据比出哪个配置更好。**
> **客户端的活 = 先用默认配置跑起来 → 登录后拉取服务器分给这个玩家的方案 → 按方案展示 → 玩家真正接触时打曝光 → 玩家行为上报。**
> **DataMaster = 帮客户端把「拉方案、存方案、读方案、打曝光、报事件」这几件事封装好的工具。**

在 Nova 里，这套能力由 `DataMasterPlugin` 承载，接入方式见同目录 `DataMasterPlugin.md`。
