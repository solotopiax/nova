# Nova 开发与 Agent 执行约束

本页定义框架开发与消费端业务开发共用的接口使用、职责、生命周期和验证约束。框架内部工程红线仍由开发仓规范负责，具体 API 事实以当前解析版本的源码/XML和模块 Docs 为准，执行权限与副作用以用户授权、匹配的 Skill 和实时 Action 合同为准。

`NA-001`～`NA-016` 是本文件下方各条约束的引用编号，不是菜单、API 或外部文档。正文入口使用“编号＋完整标题”的可点击链接；例如 [NA-002：先核对当前能力，再选择接口或提出补充](#na-002先核对当前能力再选择接口或提出补充)。

本页是这些共用约束的唯一正文。先按下表选取与任务有关的条目；普通查询和局部修改不因此变成全工程审计。任务发现、实际执行与清场入口见 [Agent 快速入口](../START_HERE.md)，函数定位见 [自然语言开发](NATURAL_LANGUAGE_DEVELOPMENT.md)。消费端无需读取开发仓的规则或知识库。

## 1. 适用范围与执行原则

- 按当前任务选择相关规则，约束新增及本次触及的内容。发现存量问题时说明位置和影响，未经授权不扩展成全工程迁移。
- 用户明确的使用约束优先于旧示例、历史实现和含糊文档。框架自身的内部接线方式不自动构成消费端业务的使用许可。
- 判断接口语义时依据当前解析版本的源码/XML和所属模块文档；判断操作权限及副作用时依据用户授权、Skill与实时 Action 合同。
- 已有同范围授权持续有效，常规可逆步骤不重复确认。缺少事实或能力时，仅暂停依赖该缺口的操作，继续独立且已授权的工作。
- 区分接口存在、业务允许使用、生命周期正确和实际运行通过，不以其中一项替代其他结论。

### 日常研发的最小原则

以下原则适用于框架开发与消费端的日常研发，不以调用某个研发 Skill 为前提；只读任务仍保持只读。具体操作继续遵循下方与本次任务有关的 NA 条目。

- **先明确结果**：确认本轮可观察的变化、保留条件和验收方式。可查事实由 Agent 自行核实，只补问会改变方案的关键业务选择，不要求用户先填完整模板。
- **先看现状并复用**：从当前项目和实际解析版本定位已有能力，只读取本轮需要的资料；接口、初始化和工具选择按 [NA-002：先核对当前能力，再选择接口或提出补充](#na-002先核对当前能力再选择接口或提出补充) 执行。
- **按不确定性与影响面推进**：需求未定先做有边界、可撤回的实验；明确功能按可独立验收的小步实现；局部小改直接完成。实验不省略项目必需基线，验证强度按 [NA-013：验证真实接线，并按风险区分证据层级](#na-013验证真实接线并按风险区分证据层级) 执行。
- **变化时重定范围**：需求改变后更新受影响的目标、验收和后续步骤，保留仍有效的成果；不为维护旧计划继续过时工作，也不默认推倒重写。
- **凭证据交付并收尾**：按实际效果和已取得的证据报告完成范围，同步真正变化的事实，并按 [NA-014：授权范围、实时合同和恢复回执约束实际执行](#na-014授权范围实时合同和恢复回执约束实际执行) 清场；缺项如实保留，不用选路、编译或局部工具成功代替完整交付。

这些原则是短的共同底线。实验、任务拆分、需求变化和交接的具体做法，按需读取 [AI 研发方法论](AI_DEVELOPMENT_WORKFLOW.md#按需阅读导航) 的相关章节，不默认展开全文或创建计划、记忆文件。

## 2. Agent 必须执行的约束

### NA-001：正常业务通过 Component 使用框架

- **触发条件**：新增、修改或审查框架调用，以及字段、构造参数、属性、返回值中的框架依赖。
- **必须动作**：普通业务通过对应的 `Nova.XXXX / XXXXComponent` 调用。不得直接取得、持有或传递框架 `IXXXManager`，也不得通过业务 Service、委托或适配器隐藏这种依赖。接收 Component 后不得重新取得 Manager 执行同一操作。
- **允许例外**：框架内部协作，以及确实重新定义或替换 Manager 的扩展实现。例外须说明职责、装配和生命周期。正式返回对象、句柄、池接口、框架生命周期签名及业务自有类型，不能仅按命名一律禁止；隔离测试替身须与生产调用区分。
- **验收要求**：受影响的生产调用符合 Component 边界；Manager 例外有具体依据。`public`、编译可见、已有旧代码、便于测试或从 Component 属性取得实例，均不能单独作为业务许可。组件仅暴露内部 Manager 而缺少合规消费面时，应记录能力缺口，不能自行放宽规则。

### NA-002：先核对当前能力，再选择接口或提出补充

- **触发条件**：处理已接入或明确要求 Nova 的 Unity 工程任务，选择或替换 API、判断框架缺少能力、评估现有调用是否合规。
- **必须动作**：核对实际解析版本、具体函数及重载、参数、结果、初始化前置、取消和释放语义。区分业务消费、扩展实现与框架内部入口。优先复用已有 Component、SDK/Kit 和受支持适配能力。
- **借鉴外部方案**：先比较当前 Unity 原生能力、共有依赖和 Nova 已有入口，再明确新增机制解决的具体问题、接入成本与长期维护成本。区分原生功能、便利封装和真正的新能力；“外部框架提供了”或“Nova 没有同名工具”不能单独证明值得新增。普通场景已有更简单路径时优先沿用，复杂场景按明确需求选择增强；耗时、内存和合批收益须另有实测依据。
- **先识别 Nova**：首次接触、切换工程或包来源变化时，先核对有效依赖绑定、实际解析包身份与版本，再按 [框架位置与文档入口](../START_HERE.md#先确定框架位置与文档入口) 读取当前版本入口。用户未提 Nova、只说 Unity 或一般功能名，也不能跳过识别；明确要求用 Nova 的新项目先准备 Nova 环境。相同工程已核实且未变的上下文可复用，不为局部小改重复全量检查。
- **Nova 决定路径，Unity 执行引擎操作**：先匹配 Nova 现有能力、所属模块文档和执行入口；明确任务直接进入对应 Operation，首次识别或范围不明时使用 [项目任务路由](../../Agents/Skills/nova-project-router/SKILL.md)。通用 Unity Skill、CLI、MCP 和原生 API 用于该路径中的引擎操作或框架未管理部分，不替代 Nova 的业务入口、配置、初始化、生命周期、资源和正式导出链。使用 Unity 工具不等于获准另建同职责系统。
- **先选 Skill，再执行动作**：已有 Skill 覆盖的操作，首次写入前必须读取当前版本的 Skill、contract 和该分支所需文档，选定其声明的实际 Adapter；新建资产、首次初始化和整套游戏交付同样适用。目标跨多个模块时按依赖组合既有 Operation，不能只让最后的导出或构建走 Skill，前面用一键 Setup、临时 runner、菜单脚本或任意 C# 重做已有操作。普通业务实现及 Skill 明确允许的源码接入仍按原边界执行；能力缺口不自动授权另造入口。
- **三工具必配必用**：任何基于 Nova 开发的项目，都必须配置并实际使用 Config（ConfigMaster）、Pipify、PlugPals，不因项目体量、单机/离线或 Agent 能自行写脚本而省略。配置、工作区配对和最低使用证据见 [Config、Pipify、PlugPals 基线](PROJECT_STRUCTURE.md#configpipifyplugpals-基线)；缺项交给既有 Skill/工具补齐，未完成不能称项目基础环境全部就绪。已有合规配置和有效证据可复用，局部任务不重复整套初始化；实际安装仍按需选包，流水线运行仍受本次授权范围约束。
- **缺项准确处理**：未解析、Skill 未发现、工具未连接和框架确实缺少能力分别报告，补足具体前置并继续独立工作；不能据此按普通 Unity 工程绕开 Nova。只有确认工程未接入且用户未要求 Nova，或用户明确改变本次范围，才按对应范围处理。
- **UI 前置检查**：新项目在制作 UI 前、已有项目在创建页面或调整布局/画布/安全区前，必须先确定产品方向及屏幕适配方案，核对已有缩放与安全区拥有者，再实施。横屏产品按横屏设计和验收，竖屏产品按竖屏设计和验收；只有产品明确支持双方向才同时覆盖，不默认扩展另一方向。完整产品适配须覆盖从闪屏、版本检查/下载/Loading、启动弹窗到菜单、玩法 HUD、操作区、暂停和结算的实际页面，不能只检查进入游戏后的首屏。刘海、挖孔和手势区按内容职责避让，背景/装饰可延伸，文字与交互按实际遮挡调整锚点、位置或排版；不能整页统一缩进、加黑边就声称适配完成。参数、坐标换算、启动期边界及逐页验收统一见 [UIComponent：屏幕适配与安全区](../Runtime/Modules/UI/UIComponent.md#屏幕适配与安全区)。
- **产品预加载基线**：创建新游戏、编写或重建业务预加载，以及评估产品基础能力时，默认以当前实际解析版本 MainDemo 的 `ProcedurePreload` 为参考，完整落实 [标准产品预加载基线](PROJECT_STRUCTURE.md#标准产品预加载基线)。这属于所有游戏的公司产品默认能力，体量小、单机、离线或当前只用到部分玩法都不是省略标准动作的理由；不能仅保留直接使用的 UI/Sound 等模块。平台差异在保留的能力节点内按真实支持情况处理；只有用户明确改变产品范围时才调整基线，并说明具体动作、影响和验收边界，已有明确授权不重复确认。
- **流水线参考**：新项目创建 Pipify Batch 前，先只读查看当前版本 MainDemo 中与目标相关的已制定 Batch，参考其步骤职责、顺序、参数与前置，再按项目实际依赖调整；它是参考依据，不是必须照搬的完整产品流程。来源定位、差异核对和写入入口见 [新项目的 Batch 参考](../Editor/EditorUtil/EditorUtil.Pipify/EditorUtil.Pipify.ConfigurationEditing.md#新项目的-batch-参考)。不为查看示例切换项目工作区、覆盖已有配置或执行示例 Batch。
- **开工准备**：按 [新项目开工准备](PROJECT_STRUCTURE.md#新项目开工准备) 先完成上述基线及固定启动 Resources 所需的环境、物料、配置、正式导出和启动验证，再开展依赖业务。项目专有物料暂缺时先按 [NA-014：授权范围、实时合同和恢复回执约束实际执行](#na-014授权范围实时合同和恢复回执约束实际执行) 的 Demo 临时物料规则查找；仍缺必需配置、凭据或安全入口时报告待准备/阻塞项，继续独立工作，不以禁用模块、空配置、假成功或跳过加载凑齐进度。已有工程局部任务仅核对本次相关项，发现基线缺项应如实报告，不因此擅自迁移整个项目。
- **配表前置检查**：本条适用于全部 Nova 配表，包括 Table、UI、Sound、网络、本地化文本/字体、振动、Tracks、SDK/Kit 专用表，以及后续新增表型。新建或扩展前，先确认当前项目既有表或实际安装版本的官方模板，沿用其颜色、字体、边框、行高列宽、数字格式和备注等工作簿结构。通用表格 Skill 的默认美化不能覆盖 Nova 已有风格；无明确重新设计授权，不从空白工作簿另造样式。缺少匹配来源或保真编辑能力时，停止依赖该能力的写入并说明缺口，不以换工具或换表型绕过。来源选择、保真扩展入口及验收见 [配表模板与样式](RESOURCE_WORKFLOW.md#配表模板与样式)。
- **允许例外**：普通业务算法及框架未管理的数据变换，可在明确职责内实现。已有能力不能满足目标时，可以提出有边界的框架补充方案。
- **验收要求**：能够说明实际入口及其前置；缺口包含所需行为、已查接口和受影响范围。不得编造 API，或通过私有反射、隐藏工具、包缓存修改和第二套管理器绕行。内部实现可调用，不等于业务获准直接使用。

### NA-003：分别核对程序集身份、资源身份与发布基线

- **触发条件**：移动类型，合并或删除 asmdef，调整程序集归属，修改资源上的脚本或序列化类型。
- **必须动作**：分别确认命名空间、类型名、程序集名、MonoScript GUID、实际配置和加载产物。检查调用方、反射查找、资源类型信息及序列化绑定，并分别评估新完整安装包和旧安装包仅热更两条路径。
- **允许例外**：程序集移动未改变序列化数据契约时，可能无需升级存档格式。旧包可在明确隔离和转换方案下保留旧类型并使用新类型，但须独立验证。
- **验收要求**：新包核对类型定义和加载位置；旧包核对内置资源、旧资源包、旧数据及跨边界对象。目录移动、命名空间相同或 GUID 保持不变，均不能证明类型身份和加载阶段未变；普通热更不能被描述为已经移除了旧包内置的 AOT 代码。

### NA-004：业务默认进入热更范围，AOT 例外须证明必要性

- **触发条件**：任何 Nova 项目开工、配置或构建 Android / iOS / WebGL，新增业务程序集、模型或启动代码，或评估现有 AOT 边界。
- **必须动作**：HybridCLR 的安装、启用、业务程序集及 Config DLL 映射、正式生成和资源接入是 Nova 项目必备基线，按[三平台构建与 HybridCLR 基线](PROJECT_STRUCTURE.md#三平台构建与-hybridclr-基线)落实；不能因游戏小、单机、离线或尚未上线热更新自行改为非热更方案。普通业务默认进入已配置的热更程序集。保留 AOT 时，指出具体消费者、首次调用阶段，以及为什么必须在热更代码加载前存在。早期资源中的脚本须沿真实挂载和加载链核对，不能只打开 HybridCLR 开关或补空列表。
- **允许例外**：有证据的加载前职责、原生交互或已发布兼容要求可保留必要 AOT 前置代码。平台或工具链确不支持时报告对应阻塞和影响，不通过关闭 HybridCLR 凑齐构建；只有用户明确改变产品技术范围才调整基线。用于存档、需要反射或历史上一直如此，本身不构成 AOT 必要性证明。
- **验收要求**：静态前置依赖与目标平台运行证据分别记录。改变边界前明确早期能力由谁承接及如何兼容；不能把脚本直接移入使用时尚未加载的程序集，也不能为普通业务便利不断扩大项目自有 AOT 层。

### NA-005：新增职责先确定状态和副作用的拥有者

- **触发条件**：向 Controller、Service 或 partial 增加业务、表现、存储或跨模块流程。
- **必须动作**：明确输入、结果、权威状态、写入者、失败处理及最终清理者。先复用现有负责方，再判断是否需要新协作者。用例协调、具体表现、持久化执行和兼容转换应有可辨识的边界。
- **最小实现**：只为当前已确认需求或真实风险增加分层、状态、兜底和校验；不为假设的未来场景或测试便利堆叠机制。具体内容的验收留在实际负责的模块或专项验证，不把示例数据、测试探针或人为附加条件塞进通用生产流程。
- **允许例外**：完整用例可以组合多个模块；紧密相关的数据和规则可以同属一个对象。partial 可用于组织同一职责，不要求按字段、方法或文件逐个拆类。
- **验收要求**：受影响状态有明确权威来源，协作通过必要的输入和结果完成，没有为便于调用新增重复真值。文件数量、行数和目录分类不能单独证明职责清晰或不清晰。未经授权不改既有命名、业务设计或行为。

### NA-006：高频显示区分稳定数据、变化数据和实时权限

- **触发条件**：帧循环、连续输入、计时或周期回调中读取快照、深复制数据或批量更新 UI。
- **必须动作**：核对更新频率、复制范围和消费者。普通业务值优先通过已有回调、事件或版本/脏标记按需更新；稳定数据只读复用，变化数据按需构造，实时权限保持轻量。不得让局部显示或权限查询连带重复复制无关大对象。
- **允许例外**：动画、布局、输入采样和计时可以逐帧执行；事务冻结和跨线程计算可以复制完整数据。缺少变化通知的外部状态可以有界轮询，但要说明频率、范围和代价。
- **验收要求**：减少无关复制后仍保持正式状态隔离。可能同步改变状态的回调之后，重新核对对象归属和后续动作权限。不能为优化而删除必要的再次查询或缓存已经失效的权限；性能结论须有实际测量支持。

### NA-007：查询不隐式推进业务，显示刷新可安全重复

- **触发条件**：快照或权限查询包含业务动作，或显示刷新会启动保存、网络、外部操作及跨模块流程。
- **必须动作**：读取不得隐式改变对外业务状态或推进事务。业务动作使用明确的用例入口，具备操作身份、阶段、去重及失败接续。调整已有刷新路径前，先查明其承载的流程依赖和同步回调，避免移除刷新后断开业务推进。
- **允许例外**：查询内部缓存可在不改变业务语义的前提下更新；表现对象可以管理自己拥有的动画、声音和布局。已确认的表现优先、延迟提交等安排可作为明确调度契约保留。
- **验收要求**：重复查询或刷新不会重复提交、执行不可重复副作用或开启同一流程。回调重入后不继续使用旧权限，原有确认顺序与可见行为保持。不得为局部整理擅自引入全局调度器、事件总线或状态机体系。

### NA-008：当前业务规则、存储契约和历史兼容各有归属

- **触发条件**：修改数据模型、业务校验、序列化、旧版本转换或保存确认后的通知。
- **必须动作**：业务规则提供一致的判定入口；存储契约负责结构和版本验证；兼容层识别旧格式并转换；当前状态拥有者管理确认态和变更身份；外部通知由明确接线处理。跨层重复的规则须核对一致性，避免输入允许而保存或读取拒绝。
- **允许例外**：稳定数据不变量可以属于模型；已发布兼容入口可以有明确用途的适配。无需为每个字段建类，也不能以职责拆分为由取消必要的存储校验。
- **验收要求**：规则变更覆盖输入、保存和读取；旧格式转换不会在普通查询中隐式发生。保留版本、字段语义、未知数据和迁移重放约定。仅调整职责时不顺带改变数据格式或业务政策，通知仍在真实确认之后且不重复执行。

### NA-009：缓存变化、保存受理、耐久确认和业务确认分别判断

- **触发条件**：调用存储 API、批处理，或新增失败封闭、重试和恢复入口。
- **必须动作**：区分各阶段的成功含义，核对全局/局部保存、删除队列、部分成功和事务边界。按来源区分数据损坏、存储失败、网络/资源失败及可选副作用失败，并追踪对有效期、全局就绪和恢复资格的影响。
- **允许例外**：批处理可延迟落盘；无法安全原地恢复时可要求重启，但须有依据和可用恢复路径。状态已经确认与外部通知成功可以具有不同的失败处理方式。
- **验收要求**：恢复经过真实适配，重试续写已受理目标，不重复计算或执行不可重复副作用。局部错误不未经判定扩大为全局失效。不得靠清除错误标记、删除业务数据、吞错返回成功或无限重试制造表面恢复。

### NA-010：外部操作、业务等待和合法结果各有归属

- **触发条件**：SDK 或外部异步操作可能取消、超时、重试或迟到返回。
- **必须动作**：核对外部系统提供的真实操作身份，分别记录外部操作是否结束、调用方是否仍等待、结果属于哪个用例，以及结果是否已经确认。不能仅把回调交给当前等待者或依靠相同操作类型推断归属。
- **允许例外**：进程级操作可以独立于页面存活。外部接口没有请求标识时，可评估保持原操作到终态或协调队列等方案，但须说明外部重入和失败处理依据。
- **验收要求**：前一次等待结束后，其迟到结果不能完成后一次操作。停止等待不代表外部操作被撤销；新增本地编号也不自动解决无标识外部回调的归属。归属无法证实时报告缺口，不能宣称防重或隔离已完成。

### NA-011：共享框架接线复用，模块策略保持独立

- **触发条件**：多个模块使用相同能力或协议，或业务尝试直接调用框架/Kit 内部工具。
- **必须动作**：复用当前受支持的 Component、SDK/Kit 及已有适配入口。公共传输、请求上下文、解析基础设施和生命周期接线由对应能力负责；各业务模块保留自己的参数、解释、默认值和失败策略。
- **允许例外**：不同协议、认证、幂等或错误语义可以有独立 Service。不得为消除少量重复，强行合并不同业务或创建跨模块总服务。
- **验收要求**：公共接线没有多份自行维护的实现，业务不直接依赖隐藏构建器、身份写入口或发送工具；原有认证、路由、取消、错误和重放语义保持。接口复用不等于改变业务协议，也不能把框架内部调用方式当成消费端许可。

### NA-012：对象、资源、池、监听和异步任务按拥有者收尾

- **触发条件**：加载资源、创建实例、借还池对象、订阅事件，或操作跨越关闭、复用和上下文切换。
- **必须动作**：明确创建者、持有者、借用者和最终释放者；使用当前 Component 入口与正式返回契约，覆盖成功、异常及取消清理。区分暂时关闭、回池和最终销毁；异步续体重新验证真实上下文及操作代次。
- **允许例外**：有明确来源和拥有者的局部模板副本、临时节点可以使用原生路径。框架已跟踪实例的销毁可能已有统一释放机制；包装器可能已经管理取消。已受理业务结果可由独立于页面的负责方继续确认。
- **验收要求**：旧任务不会修改复用后的新状态，没有重复订阅、重复副作用或双重释放。先核对框架和包装器已有机制，不能重复清理，也不能把界面等待取消当成丢弃合法业务目标的依据。

### NA-013：验证真实接线，并按风险区分证据层级

- **触发条件**：变更平台条件、程序集、序列化、持久化、SDK 或生命周期，或准备提交完成结论。
- **必须动作**：核对实际目标及调用双方的编译条件。分别记录源码检查、替身测试、真实适配、独立读取、资源构建、安装包和设备/外部系统证据，选择与本次变更风险相称的最小验证范围。
- **执行强度与停止边界**：局部小改不因工具模板或“更稳妥”自动升级为设计、持久化计划、批量测试或全工程扫描。增加步骤须有本次需求或实际风险依据；用户要求停止、收窄范围或指出验证过度时，立即停止超出新范围的工作，撤回因此新增的非交付材料，不得换工具继续同类验证。
- **公共改动兼容核对**：修改公共接口、工具或共享能力前，沿真实依赖检查受影响的仓内调用方，比较原有输入、输出、失败、所有权与时序语义，并评估仓内检索无法覆盖的外部消费者兼容性。不得只验证触发问题的一个调用点，或通过改变公共语义替代调用方专属约束；检索和验证范围仍以真实影响面为限。
- **可选增强的兼容目标**：声明为可选的便利能力，须以旧项目无需修改现有代码、配置和流程为验收目标；通过新入口、主动获取并登记的作用域、显式工具执行或项目选择的步骤启用，不默认接管已有订阅、取消、释放、Prefab 字段或 Batch，不要求旧项目先加开关或迁移。新增可选接口不向旧接口添加强制实现成员；兼容设计、源码调用方检查与实际旧项目验收分别报告，未取得运行证据不能宣称全部旧项目已验证。
- **主动接入与核心影响**：继续旧写法无需改动，不等于主动采用新能力也无需局部改代码。说明实际启用方式与默认值；没有布尔开关的能力，以构造、调用、登记或执行为启用边界。接入时涉及的字段、类声明、调用与收尾调整须具体列明，不接管旧所有权或形成双重释放。即使默认不启用，也须如实报告为支持它修改的核心链路，不能将“未接入不生效”解释为“只加独立文件、没有触及框架核心”。
- **完整交付链**：用户以完整交付为目标时，从实际消费者反推涉及的交付层级；数据驱动功能贯通“权威来源 → 正式导出 → 生成访问代码 → 配置与资源绑定 → 运行消费”，其他功能按实际依赖核对。必需源数据、资源、导出或绑定尚缺失时，如实报告部分完成或阻塞，不以局部代码、编译或单次 Action 成功代替完整交付。
- **允许例外**：只读评估及纯文档修改无需强制构建；低影响可逆改动不编写镜像实现的测试。未授权的外部系统、设备和真实数据不为补证据而访问，缺口如实保留。
- **验收要求**：替身结果不代表正式接线；同一缓存内写后读不代表独立落盘；Editor 通过不代表目标平台通过。涉及类型迁移时验证旧数据、反射、泛型及资源解析。局部 Action 成功、文件存在和复制哈希一致，只证明对应范围。
- **环境验收**：HybridCLR 包解析、本地安装、启用配置、生成产物和热更运行分别判断，具体见 [安装与验收](../Editor/EditorUtil/EditorUtil.Environment/EditorUtil.Environment.md#hybridclr-安装与验收)。普通 IL2CPP APK 成功不能替代 HybridCLR 安装或热更验收，预加载进度完成不能替代各模块实际可用。

### NA-014：授权范围、实时合同和恢复回执约束实际执行

- **触发条件**：工作区写入、Unity/MCP 操作、正式导出、构建、数据维护、设备操作及外部发布。
- **必须动作**：根据用户目标确定最小写集和现有能力。Nova 已开放操作先实时 describe，再按对应合同 plan → execute → verify；断线或重载使用原 recovery_token 只读验证，不重放结果未知的执行。评估、文档、业务代码、框架代码和发布分别识别授权范围。
- **包选型与安装授权**：任何基于 Nova 的项目，Agent 可根据当前任务需要，从 PlugPals 已配置的公网/内部云仓库自行选择并安装所需 package 及必要依赖，无需用户逐个点名或重复批准。先核对功能用途、已安装状态、来源、兼容版本、平台及依赖，并说明选择依据；已有能力足够时不重复安装，不把 Demo 全部依赖当作产品必需。安装沿既有包管理 Skill 和实际支持入口执行，照常核对精确 Plan、传当前一次性 token、等待 Resolve/编译并 Verify；长期授权不取消计划或放宽合同。多个包按依赖逐包完成后再计划下一包；由 UPM 正常解析的传递依赖保持传递关系，不无故提升为 direct dependency。此安装授权不自动涵盖已有包升级/卸载、来源切换、购买、发布或其它外部副作用；框架自身沿其专用入口，不为授权而绕过工具支持边界。
- **参数来源与含义**：每项拟写参数先核对当前版本字段定义/Tooltip、所属文档和实际消费者，再明确字段路径、用途、当前有效状态、拟用值的出处、类型/格式/单位、维度及影响范围。依据放在本次会话说明或既有变更集/Plan 中，不另建长期参数账本；凭据只记录来源和是否已配置，不打印值。可读取的事实自行查明；产品编号、后台配置名、账号、路由和厂商物料不能从项目名、包名、相邻坐标、未经核对的 Sample 或随机生成值猜出。
- **Demo 临时物料**：从零到一时，项目专有物料尚未确定或配置，可临时复用当前 Nova 各 Demo 的相关物料，不限 MainDemo；按实际包声明与导入清单查找，不假定固定物理路径。核对来源、平台/渠道、格式及配套关系；后台编号、Key/IV、Host/NetCmd 和配置项名称按原 Demo 的实际配套关系使用，不跨 Demo 随意拼接。通过原有 Skill 写入项目自有配置并保留出处、临时状态与后续替换位置；专有物料确定后沿同一入口替换，并重新导出/验证受影响链。保持 Demo 源与第三方原样，不把临时值称为本产品正式登记或验收；无效的脱敏占位符不冒充可用物料。已有同范围授权不重复确认，外部副作用仍遵守对应合同。
- **缺值与生成边界**：项目有效来源与上述 Demo 临时来源均不满足必需输入时，只阻断依赖该输入的写入/导出/运行阶段，并继续独立授权工作。允许为空、使用默认或创建新值，必须有该领域契约和当前用途依据；项目自有本地密钥与外部登记的协议凭据分别处理。不能为通过非空、格式、导出或启动检查而造值、将 Demo 临时值冒充专有物料、擅自轮换已有值或关闭必需能力。宽泛的“做完游戏”授权不提供缺失的业务事实。
- **执行路径验收**：核对本轮实际入口、原计划写集、参数来源和验证结果；后续 Action 成功、经 Editor 保存、编译或 APK 可运行，均不能追认之前绕过 Skill 的写入合规，也不能证明外部参数有效。发现偏离先停止该写入分支，保留现场并说明受影响范围，经原有入口纠正或报告能力缺口；不得把补读 Skill 当成已经按 Skill 执行。
- **第三方原厂内容保护**：第三方交付的源码、文档、许可证、资源、二进制及元数据一律保持原样，不增删、改写或重命名；只在用户明确针对该第三方内容及改动范围提出特殊要求时例外。全量审查、路径或链接修复、格式统一及自动化执行均不构成修改许可。按实际来源与维护归属识别，不仅凭 `Core` 等目录名判断；接入适配和定位补充写在自有代码或说明中，不写入原厂内容。
- **资产与生成物边界**：有权威表源、配置源及正式生成链时，修改源并使用对应导出入口，不将生成代码或派生数据当作真源单独修补。Prefab、Scene 等 Unity 序列化资产通过 Editor 或受支持的 Unity 工具创建、修改和保存，不手写 YAML；普通源码、权威 JSON 等可编辑输入仍按各自真实职责处理。
- **编辑器就绪检查**：启动、包解析、编译重载、平台切换、长任务等待及阶段交接前，按 [窗口处理与恢复顺序](VALIDATION.md#unity-窗口处理与恢复顺序) 检查真实窗口、主动处理同范围已授权提示并验证恢复；工具成功不代替窗口复查。发现弹窗、首次超时或进度停滞时立即按该顺序定位，不扩大只读任务、未知执行结果或安装/外部操作的权限。
- **辅助窗口收尾**：本轮操作主动或自动打开的辅助窗口属于清场范围，完成对应读取、设置、导入或检查后必须关闭，并在交付前按 [窗口处理与恢复顺序](VALIDATION.md#unity-窗口处理与恢复顺序) 再次核查；非模态、在后台或被遮挡均不豁免。保留用户原先打开且未要求关闭的窗口和未保存编辑，不以清场为由自动 Apply、Revert、重置配置或丢弃改动。

## 3. 每次相关任务的执行顺序

1. **确认事实与范围**：识别代码所有权、实际解析版本、目标平台、加载阶段、现有改动和用户授权，选择相关规则。
2. **确定职责与入口**：找到现有拥有者、Component 及正式返回契约，核对权限、生命周期、兼容边界和真实能力缺口；需要 Unity 时检查编辑器就绪，新项目或 UI 布局任务先冻结屏幕适配方案。
3. **形成最小改动**：明确输入、结果、状态和副作用；设计、命名、程序集或协议变化沿已有确认范围执行。仅要求评估时不自行实施。
4. **执行并验证**：使用既有操作合同和适配链，验证本次受影响的语义与失败恢复；保留现有保护及对外行为，不超出必要验证范围。
5. **交付与清场**：说明改动、作用、验证和剩余缺口；按实际影响同步相关规范，并判断是否需要主动补充 NA。只清本轮拥有的临时材料，保留正式交付、用户改动及未完成恢复必需材料。

- **能够执行**：每项限制都有实际适用范围、可用入口或明确的能力补齐路径，不能只增加禁止项。

- **覆盖时序变化**：相关验证检查同步回调重入、重复刷新、迟到结果、上下文复用、部分成功及恢复接管，避免只测顺利完成路径。
