# Minds 工作指引

## 角色

`Minds/` 是 Nova 的长期知识层，整库随 Framework 包和公开仓分发，包括现行条目与历史归档。它存放：

- 架构决策
- 术语定义
- 可复用模式
- 快照与归档

它的默认职责是解释：

- 为什么这样设计
- 哪些术语必须统一
- 哪些跨模块约束长期成立
- 哪些历史结论仍然影响当前实现

整库分发不代表整库载入上下文。开发仓代码任务先做轻量索引匹配；消费项目在需要设计依据、术语或历史边界时按需查询。

## 起手读取

- 先从当前安装包的 [Docs/START_HERE.md](../Docs/START_HERE.md) 确认框架位置与共同约束，再读 [0-Index/0-Index.md](0-Index/0-Index.md)。
- 按目标模块、类型与行为关键词只加载最相关的 Layer 1 索引；没有直接命中就停止。
- 只有索引明确命中，或需要核查高风险改动的历史边界时，才继续读取具体条目。

开发仓维护遵循仓库入口指定的知识治理流程，高风险前置查询使用开发态 `nova-prelookup`；消费端不依赖开发仓规则或工具。

## 消费端边界

- 只读当前实际解析的 Framework 包内知识，不反向修改包快照，也不复制整库到项目规则或常驻上下文。
- 历史条目中的旧命令、开发仓路径、个人环境和内部仓引用仅用于追溯，不作为消费端执行前置；缺失的历史附件不要求从其他仓补齐。
- 已归档、退役或被替代的条目仍完整公开，其状态用于判断适用性，不能因可读就视作当前规范。
- 项目专有经验保存在项目自有资料中；框架知识的修改回到获授权的 Nova 开发仓真源。

## 查询策略

- 先索引，后正文。
- 一个索引或一条笔记够用时，不要扫描整个 Vault。
- 开发仓每次代码任务都要完成轻量匹配，但“必须检查”不等于“必须修改”或“必须展开正文”。
- 当前实现真相以 `Docs` 和代码为主。
- 本文及本目录所有 Markdown 的文件关联，统一遵循随包 [NA-015：源码、文档、知识说明和 Agent 暴露同轮一致](../Docs/Onboarding/DEVELOPMENT_CONSTRAINTS.md#na-015源码文档知识说明和-agent-暴露同轮一致) 中的“Markdown 路径与规则引用红线”。
- `Minds` 用于历史决策、术语口径、可复用规则和过去的踩坑结论。

## 优先级规则

- 在历史知识之间，正式 `ADR` 优先于一般说明性笔记；当前行为仍以核实后的源码和 `Docs` 为准。
- 如果 Vault 规则和当前代码冲突，要显式指出冲突，不要猜哪边一定正确。
- 没查到就明确说“未命中”，不要伪造历史依据。

## 默认写入策略

以下仅适用于获授权的 Nova 开发仓真源维护，消费端保持只读。

- 普通任务结束时必须判断是否产生长期知识；高置信且证据完整时，无需再次确认，直接以正式编号写入 [2-Areas/](2-Areas/) 或 [3-Resources/](3-Resources/)。
- 不使用草稿中转目录或临时编号；防重命中时优先补强或合并既有条目，证据不足、仅有实现流水账或临时状态时跳过并报告。
- 高置信知识沉淀可以自动新增正式条目，也可以补强、合并或改写 `2-Areas/**`、`3-Resources/**` 中的既有条目，完成后直接展示结果。
- 归档、删除、重编号、建立 supersedes 关系或用新决策取代已有决策属于破坏性治理，必须主动向用户确认。

写入 `Minds` 时，避免混入以下内容：

- `session_id`、自动 hook 运行痕迹
- 本地 `memory` 指针全文
- `.claude` / `.codex` / agent / hook 的具体运行细节
- 只对某一代协作工具有效的流程说明

自动正式条目必须包含可核验的来源、影响面和验证依据，不得带 `session_id` 或 hook 尾注。

用户显式调用 `nova-obs` 时，必须先运行八维只读体检，覆盖结构、元数据、编号、双链、重复、索引、生命周期和膨胀；发现破坏性治理候选后统一向用户确认。

同理，只对旧协作栈有效的 ADR/PAT 不应继续停留在 [2-Areas/](2-Areas/)，而应迁到 [4-Archives/Collaboration/](4-Archives/Collaboration/INDEX.md)。
