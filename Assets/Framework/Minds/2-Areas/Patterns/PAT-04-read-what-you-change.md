# PAT-04：「改什么读什么」分层上下文策略

## 适用场景

- 项目体量较大，源码与文档长期共存
- 需要控制阅读面和上下文成本
- 任务不是全模块重构，而是局部实现、局部修文档或局部排查

## 核心原则

**md 做导航，cs 做真相；改什么读什么，也验什么。**

也就是：

- 先用 `Docs` 判断模块入口、文件拆分、公开 API、状态机和常见误区
- 再去读与本次改动直接相关的 `.cs` 文件和代码片段
- 只有文档缺失、过期或明显存疑时，才扩大到完整源码
- 验证强度与改动风险相称：能用局部静态检查或一次视觉确认覆盖的 L0 修复，不扩大成全量测试或完整运行时链路
- 通用流程 Skill 不能覆盖 Nova 的风险分级；L0 小改不自动调用 `brainstorming`、`writing-plans`、TDD、Unity Test Runner，也不为流程完整性创建设计、计划或专用测试文件
- 根因明确、改动已生效且用户确认解决时立即收口；用户的停止信号优先于预设流程的剩余步骤

## L0 执行预算

明确的单点路径、文件名、文案、常量或一行替换，默认预算固定为：

1. 一次精确定位
2. 一次直接修改
3. 一次与目标直接相关的局部静态检查
4. 立即交付

每增加一个 Skill、测试或工具步骤，都必须指出它直接覆盖的真实失败风险。“流程要求”“更保险”或“以后可能有用”不能作为升级理由。只有发现 public API、序列化、生命周期、跨模块契约、启动链等具体风险证据时，才允许升级到 L1 / L2，并先向用户说明新增步骤和成本。

用户指出“验证过度”“只是小改”“停止测试”或同义要求后，剩余验证预算立即归零。应停止尚未开始的验证，撤回本轮因过度流程新增的测试、设计或计划产物，只保留用户要求的直接修改；不得换用另一种工具继续同类验证。

## 决策矩阵

| 场景 | 推荐策略 |
|---|---|
| 要修改某个较大的类或模块 | 先读对应 `Docs`，再按文档指向精读相关 `.cs` |
| 要修改很小的类型 | 直接读 `.cs`，改完再补 `Docs` |
| 只想调用某模块 | 优先读 `Docs` 的公开 API 和示例，不展开实现 |
| 文档缺失或已漂移 | 退回代码，以代码为准并顺手修文档 |
| 纯格式化、纯局部重命名、纯行为无变更小修复 | 直接改代码；若公开事实未变化，可不扩读整套文档 |
| 单点路径、文件名、文案、常量或一行替换 | 精确定位后直接修改，只做目标 diff、精确搜索或格式检查之一；不自动写设计、计划、测试或启动 Unity |
| 已定位的坐标、间距、对齐等 L0 视觉修复 | 修改直接相关代码，做最小静态检查或视觉确认；不自动启动完整 TDD、编译、全量测试和 Play Mode 链路 |
| 用户已确认修复、指出过度验证或要求停止 | 验证预算归零；停止新增工具调用，撤回本轮流程性产物，简洁交付结果和必要的剩余风险 |

## 小类型直读判据

满足任一即可直接读 `.cs`：

- 根类及全部 partial 合计小于约 150 行
- 体量很小的枚举、接口、配置对象、数据容器
- 文档本身比源码更冗长

## 这样做的原因

- 文档比源码更适合做入口和导航。
- 源码才是当前实现真相。
- 先导航后精读，比“上来全读源码”更省上下文。
- 改完当场同步文档，比末尾集中补文档更不容易漏。

## 反模式

- 上来就把一个模块所有 partial 全读完
- 明明有现成文档入口却完全跳过
- 文档已失真却继续盲信旧文档
- 改完代码不回刷对应文档，制造下一轮阅读噪音
- 小改动套用大流程，验证成本明显超过变更风险
- 因通用 Skill 带有完整流程模板，就把 L0 修改升级为设计文档、实施计划、TDD 和批量测试
- 用户要求停止后，改用另一个测试入口、静态检查或工具继续完成同类验证
- 用户已经确认解决或要求停止，仍机械补齐预设测试链路
