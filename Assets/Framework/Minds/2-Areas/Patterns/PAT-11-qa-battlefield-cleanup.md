# PAT-11：测试结束清场铁律与测试脚本命名规范

## 适用场景（When）

- 任意 agent 或开发者完成编译、EditMode、PlayMode、Player、脚本化检查或诊断后
- 测试成功、失败、超时、中断或中途更换验证方案后
- 任何在场景内挂临时 GameObject、修改 Inspector 字段、写 PlayerPrefs/EditorPrefs 的运行时验证
- 为执行验证临时创建 runner、菜单入口、marker、结果文件、日志、可执行文件或构建目录时
- 在被测模块附近就近创建测试脚本时（命名带「关键词+YYYYMMDD」）

## 核心做法（What & How）

### 一、清场清单（必须项）

任何测试或验证报告给出 `[PASS]`、`[FAIL]` 或完成结论前，都必须执行清场清单并逐项确认：

| 维度 | 检查项 |
|---|---|
| 场景 GameObject | 测试期间临时挂的 `__TestRunner__` / 临时调试节点 / 测试 GO 全部删除 |
| Inspector 数据 | 只恢复本轮测试改动，回到测试前实际值与原有脏状态；不得一律重置默认值或保存用户未保存的编辑 |
| Editor 菜单状态 | 临时切换的构建路径、配置开关、运行模式回滚 |
| PlayerPrefs/EditorPrefs | 恢复本轮涉及键的测试前存在性和实际值；只删除本轮新建且已确认归属的临时键 |
| 临时执行器 | 一次性 runner、菜单入口、辅助脚本及自动生成的 `.meta` 全部删除 |
| 临时文件 | marker、测试结果、日志、临时可执行文件、临时目录及测试专用构建物全部清理 |
| 生成噪声 | 动态字体图集、无关序列化变化、场景脏数据和测试缓存恢复到测试前状态 |
| 工程刷新 | 删除临时 Unity 脚本后执行 AssetDatabase/工程文件刷新，确认没有陈旧 `.csproj` 引用 |
| 场景保存 | 核对磁盘与内存状态均恢复；只保存本轮已授权的正式变化，不用全局保存把用户原有脏数据写入磁盘 |
| 最终核查 | 对照测试前基线检查 `git status --short`，并定向扫描 runner、marker、日志和临时目录残留 |

### 二、保留项

- 作为长期测试基础设施维护、或用户要求保留的正式测试资源（Prefab / SO / Texture / Audio）保留
- 工程目录中明确作为长期门禁维护的**正式测试脚本**保留
- 这两类是"测试基础设施"，跨会话复用，不属于"脏数据"

一次性 runner、临时菜单脚本、仅为本轮取结果创建的辅助程序及资源不属于测试基础设施，即使测试通过也必须删除。正式测试代码可长期维护，历史运行结果、日志、验收进度和产物快照不因此转成仓库档案。

### 三、临时测试脚本命名规范

确需新增的一次性测试脚本，其 class 名必须**同时**含两个要素；已有正式测试继续按模块和行为命名，不因复跑增加日期副本：

1. **测试内容关键词**（PascalCase 英文，体现验证主题）
2. **YYYYMMDD 日期**（运行 qa 验证的日期）

#### 命名范式

```
Test{ContentKeyword}_{YYYYMMDD}
{Module}TestOn{YYYYMMDD}_{Topic}
```

#### 示例

| 命名 | 评价 | 理由 |
|---|---|---|
| `TestPlayModeSplitAndLinkage_20260515` | ✅ | 内容（PlayMode 拆分 + 联动）+ 日期齐 |
| `AssetTestOn20260515_PlayModeSplit` | ✅ | 模块 + 日期 + 主题齐 |
| `Test` | ❌ | 既无内容也无日期 |
| `TestEnableHotfix` | ❌ | 缺日期 |
| `Test20260515` | ❌ | 缺内容 |
| `TestNew` / `TestTemp` / `MyTest` | ❌ | 内容毫无信息 |

#### 拆文件规则

- 不因本轮验证重命名或覆盖已有正式测试，也不把临时入口追加进通用 `Test.cs`。
- 新增长期用例优先进入对应模块的正式测试文件；只有主题边界独立时才新增正式文件。
- 临时脚本只服务本轮主题，结束即清理，不跨日期积累为运行历史。

### 四、qa 清场失败的处理

- 交付中清场结果缺项或存在本轮可归属残留时，继续补完必要清场，不把测试通过解释为任务完成。
- 发现场景 / Inspector 有脏数据时，先比对测试前基线，再恢复本轮副作用，不能覆盖用户原有修改。
- 测试失败、超时或方案切换不豁免清场；先清除上一方案残留，再开始下一方案。
- 无法确认某项改动是否由本轮产生时，不得擅自回滚；保留并在交付中明确列出，等待用户判断。
- 未完成事务仍在使用的计划、备份、回执与恢复标记不属于验收垃圾；按原执行工具的恢复和清理契约管理，不为追求零残留删除恢复能力。

## 为什么这么做（Why）

- **避免脏数据污染下次会话**：测试期间 Inspector 字段被改、忘了改回，下次同事打开工程看到的是"测试态默认值"，做错决策
- **避免误把测试态当生产态提交**：场景里残留 `__TestRunner__`、Inspector 数值偏移，git diff 一不小心就 commit 进去
- **避免多人协作翻车**：拉到不可用的工程状态，浪费排查时间
- **临时命名带日期 + 内容**：本轮残留可准确归属与清理；长期测试用模块和行为表达职责，不承载验收历史
- **拆出独立测试文件**：通用 `Test.cs` 越塞越大，类内动辄上千行 + 多个独立模块的 TC 混在一起；拆出单文件后，用例的"模块归属"和"验证主题"通过文件名直接表达

## 反模式（Anti-patterns）

- **静默清场反模式**：qa 报告只写 `[PASS]` 不列清场清单。问题：主会话/用户无法核对清场是否真做了，下次发现脏数据时责任不清
- **成功即结束反模式**：拿到测试结果后直接交付，遗漏 runner、`.meta`、marker、XML、日志或临时二进制。问题：验证成功却把工程留在不可提交状态。
- **失败不清场反模式**：测试超时或改换方案后把上一套临时设施留在工程中。问题：后续编译仍可能引用已废弃脚本，产生与业务无关的报错。
- **误删用户改动反模式**：为追求工作树干净而无差别回滚已有修改。问题：清场只能移除本轮可归属的副作用，不能替用户清空工作区。
- **可保留 = 不收拾反模式**：把"测试资源/脚本可保留"误读为"修改完不用收拾"。问题：可保留的是脚本和资源**文件**，不是脏数据；Inspector 数据不是文件，是序列化在场景/Asset 里的状态
- **追加进 Test.cs 反模式**：新模块 TC 直接 append 到通用 `Test.cs`。问题：文件膨胀，主题混淆，删除时不敢删（怕误伤其他 TC）
- **临时脚本归属不明反模式**：临时 class 名只有泛化主题、没有本轮标识，清理时无法安全区分已有基础设施
- **`Test20260515` 无内容反模式**：class 名只写日期不写内容。问题：同一天可能验多条规则，日期+空白内容名根本无法区分
- **临时 GO 不删反模式**：场景里挂个 `__TestRunner_W6__` 跑完不删，依赖"下次发现再说"。问题：用户提交前 git status 看到一堆场景修改，反复回滚浪费时间
- **以默认值代替测试前状态反模式**：无差别 DeleteKey、重置 Inspector 或全局保存场景，测试清场反而改变用户配置和未保存工作

## 跨项目复用提示

- 通用规范——任何 Unity 项目接入运行时验证流程都适用
- 非 Unity 项目的 e2e 测试同理：只恢复本轮改动并清除自有临时数据、缓存和进程；不能清空用户已有状态
- 关键判据：「测试结束后，工程的运行态是否与测试开始前一致」——一致即清场到位
- 交付判据：「正式产物完整 + 测试证据成立 + 本轮临时产物为零」三项同时满足；缺少任一项都不能宣称完成。
