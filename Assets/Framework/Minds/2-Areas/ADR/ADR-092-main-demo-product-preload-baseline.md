# ADR-092：MainDemo 预加载作为所有新游戏的默认产品基线

## 背景

游戏体量小或当前玩法离线，只能说明业务复杂度，不能证明产品基础能力不需要准备。将 MainDemo 视为可按眼前玩法任意裁减的示例，容易只保留 UI、声音等直接调用，遗漏公司产品需要的标准能力；仅等待若干初始化任务或看到进度完成，也不能证明产品已就绪。

## 决策

- 所有新游戏默认以当前实际版本 MainDemo 的 `ProcedurePreload` 为产品预加载基线，完整落实其八个标准能力节点。不能以小游戏、单机、离线或当前未调用为由自行删减；具体执行要求唯一维护在 [标准产品预加载基线](../../../Docs/Onboarding/PROJECT_STRUCTURE.md#标准产品预加载基线)，共用约束由 NA-002 路由。
- 参考的是能力准备与生命周期，不是复制 Demo 业务、账号或密钥。产品及渠道需要的真实配置、物料和 SDK 清单先准备，缺项按依赖报告并处理，不通过空配置、禁用模块或伪成功绕过。
- 平台差异在保留节点内按实际能力处理，不能据此删除整个模块或夸大设备能力。用户明确改变产品范围时记录具体调整、影响与验收边界；普通已有工程局改不自动扩张成全工程迁移。
- 初始化动作、真实加载结果、业务可用与设备/厂商/上架验收分开判断。不能忽略加载返回值，也不能仅凭计步完成放行；共享任务终态不等于每个 SDK 已成功，失败恢复必须使用真实可用入口。通用流程只负责模块初始化结果和所声明的平台分支；具体文本、表与字体的完整性由各自配置及专项验收负责，不将示例键或字体标记硬编码为通用启动条件。

## 后果

Agent 在开工、预加载接入和基线评估中主动逐项核对标准能力，职责仍由既有 Operation 承担。参考来源和范围一致，同时保留各模块的配置、失败与平台语义；不新增平行初始化管理器或把本次规范变更当成现有游戏已完成整改。

## 被排除方案

- 只初始化当前玩法直接调用的模块：会把临时原型范围误当产品基础能力范围。
- 直接复制整套 Demo 或按固定八步计数放行：示例内容与产品来源不同，任务返回也不证明业务可用。
- 为满足基线而安装全部演示 SDK 或伪造配置：无法证明公司产品及渠道实际需求，也不能代替真实凭据与验收。

## 来源与验证依据

- 公司游戏产品的默认基础能力要求：游戏规模不构成省略标准预加载动作的依据。
- `Assets/Samples/MainDemo/Scripts/Runtime/Procedures/ProcedurePreload.cs` 的标准动作和进入/尝试代次、取消与启动 UI 生命周期。
- [项目与场景结构](../../../Docs/Onboarding/PROJECT_STRUCTURE.md#标准产品预加载基线) 与 [开发及 Agent 执行约束](../../../Docs/Onboarding/DEVELOPMENT_CONSTRAINTS.md#na-002先核对当前能力再选择接口或提出补充) 是当前规范入口；执行通过既有 Procedure、启动场景和只读就绪 Skill。
- 本决策规定后续实施与验收标准，不记录或继承任何项目历史运行结果。
