# AI 研发方法的来源分析与取舍

本分析服务于[Nova 项目 AI 研发方法论](../../../../Docs/Onboarding/AI_DEVELOPMENT_WORKFLOW.md)，说明哪些经验值得采用、适用边界在哪里，以及哪些规则仍需在真实项目中检验。日常执行只读对应方法分支，不加载本研究正文。

来源核对时间：2026-11-12。GitHub 按 [371d7089402e6666f3cead441c52a4d6bb5f6363](https://github.com/anliuyu71/AI-Game-Development-Workflow/tree/371d7089402e6666f3cead441c52a4d6bb5f6363) 阅读，包含 README 与五份 Skill；该提交日期为 2026-08-06。TapTap 读取文章正文，页面仅显示修改月日，未据此推断年份。以下均为重新组织的分析，不复制原 Skill。

## GitHub：最值得保留的是状态所有权

原仓库用设计、架构、路线图和长期记忆承载不同信息。优先更新已有正文、显式保留未知、避免把对话流水当长期知识，都有维护价值。问题不在于文档数量少，而在于每个事实能否找到唯一所有者，并在变化时更新。[README](https://github.com/anliuyu71/AI-Game-Development-Workflow/blob/371d7089402e6666f3cead441c52a4d6bb5f6363/README.md)

但四份文档不能同时成为当前实现的最高事实来源。设计描述的是希望实现什么，源码与有效配置说明当前机制，运行观察说明本次发生了什么，历史记录解释为什么选择。混在同一记忆里容易出现“文档写了，所以功能已完成”的误判。Nova 采用按职责分配事实源，而不要求消费项目复制四个固定文件。

### 作者后来指出的失败条件不能略过

最新补记指出，需求持续变化、玩法需要边写边确定、模块边界不清时，原先的顺序很难使用。这不是通过增加文档就能解决的问题：如果输入尚未确定，后续架构与路线图只是把假设写得更完整。[最新补记](https://github.com/anliuyu71/AI-Game-Development-Workflow/commit/371d7089402e6666f3cead441c52a4d6bb5f6363)

因此本方法把学习循环放在实施循环旁边：未知时先产生能改变决策的反馈；明确后才扩大实现。需求变化时可以回到目标和实验，而不是单向传递文件。模块边界来自真实责任和反复验证，不来自提前填完的文档结构。这个改造是工程推导，还需用项目实践检验效果。

## TapTap：把有用习惯改成条件化规则

该文提供了沟通、分阶段实现、上下文、运行验收和经验维护的建议，也给出固定轮数、行数、批次及效率说法。这些是作者的经验范围；文章没有为阈值或倍数提供受控比较。[文章正文](https://www.taptap.cn/moment/780475308829576602)

下表是对这些主题的工程判断，而不是对原文的逐条照搬：

| 主题 | 值得采用的核心 | 应如何约束 |
|---|---|---|
| 上下文 | 让 Agent 知道目标、规则和相关现状 | 提供足够且准确的信息；全量加载可能增加噪声、成本与过时事实 |
| 分工 | 产品取舍和最终接受需要人负责 | AI 可以提出设计备选与反例，意见作为假设，由实际反馈判断 |
| 具体需求 | 给出可观察结果与关键规则 | 数值可查就查，确需业务选择才问；未知不能伪装成精确参数 |
| 分阶段实现 | 尽早获得可运行反馈 | 按用户结果纵向拆分；影响核心判断的视觉、手感和平台问题前移 |
| 质量门 | 编译、运行、日志和行为各有作用 | 根据目标选择证据，区分既有警告，不用全部清零代替影响分析 |
| 跨会话恢复 | 保留稳定决策和当前状态 | 根据上下文漂移或交接需要总结；不以轮数当可靠边界 |
| 模块化 | 降低理解与改动的耦合 | 按责任和依赖拆分；行数只能提示阅读成本，不能决定结构 |
| 素材与大文件 | 控制无关输入 | 使用检索、片段与必要图像观察；视觉任务不能拒绝看图 |
| 配置迭代 | 降低试数值的修改成本 | 复用当前权威配置和正式导出链；覆盖、烘焙是否合适由项目决定 |
| 经验回收 | 让反复出现的问题形成防线 | 沉淀有证据、可复用的根因；小修和调试流水不必永久保存 |

这些修正共同解决一个问题：经验法则常把“在作者当前项目里有用”写成“所有任务都必须这样”。将它们改成触发条件、可验证结果和例外，才适合进入 Nova 的日常研发入口。

代码行数和文件数量描述产物规模，不能说明功能价值、可维护性或净效率。判断提效还需知道没有该流程时的投入，以及审查、返工、质量和工具成本；作者的案例不包含这个对照。方法中不使用其效率倍数作为目标或承诺。[文章案例](https://www.taptap.cn/moment/780475308829576602)

## 用一手研究校准结论

研究只支持其设计与样本覆盖的结论。下列结果用于约束推断，不用于证明本文整套方法已经有效。

| 证据 | 实际观察 | 可以支持什么 | 不能推出什么 |
|---|---|---|---|
| METR，2025 随机实验 | 16 位熟悉项目的开发者、246 项任务，在当时工具条件下允许 AI 的任务用时增加约 19% | 主观变快感可能与实际耗时不同，必须计入审查和返工 | AI 对所有开发者或当前工具都减速 |
| 三家公司开发者现场实验，2025 论文版本 | 4,867 位开发者，早期代码补全工具的合并估计显示完成任务数增加 | 一些真实开发环境能获得收益，收益会随人和任务变化 | 当前自主 Agent 必有相同比例收益，或任务数等于质量和业务价值 |
| AGENTS.md 研究，2026 v3 | Python 修复基准中，规则文件的成功率差异不显著；自动生成文件增加推理成本 | 新增规则应补必要信息，并观察成本和行为 | 所有规则无用、越短必然越好，或已有必要约束可以跳过 |
| Agent 系统扩展研究，2026 v3 | 260 配置、六类基准，收益受任务依赖与协调方式影响；软件基准的新增样本小 | 按独立性、关键路径和整合成本决定是否并行 | 固定最佳 agent 数、任意任务多开就快，或基准收益等于研发产能 |
| DORA 2025 | 调查观察到 AI 使用与交付吞吐、稳定性存在不同方向的关联 | 效率和质量应一起观察，组织条件值得关注 | 相关性证明 AI 或某项流程造成结果 |

对应来源：METR [原始实验](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)；三家公司[作者论文](https://www.mertdemirer.com/Papers/Demirer_AI_productivity.pdf)；[AGENTS.md v3](https://arxiv.org/html/2602.11988v3)；[Agent 系统 v3](https://arxiv.org/html/2512.08296v3)；[DORA 2025 原发布](https://cloud.google.com/blog/products/ai-machine-learning/announcing-the-2025-dora-report)。

METR 的 2026-02-24 后续更新指出，新的观察受到参与选择和并行计时问题影响，不能可靠估计当前 AI 的提效幅度。因此上表的 19% 必须连同实验条件及[后续更新](https://metr.org/blog/2026-02-24-uplift-update/)理解，不能当作当前模型能力结论。

工程上的独立验收原则还参考 [Building effective agents](https://www.anthropic.com/research/building-effective-agents)：从简单实现出发，用环境反馈、测试与必要审查检查结果，再按实际收益增加复杂度。这是工程指导，不能把它当作“独立 reviewer 必然提升多少成功率”的随机实验证据。

两项现场实验的方向不同，说明场景和工具条件值得区分；不应只选符合自己预期的一项。基准实验对所测设置提供依据，迁移到 Unity、Nova、长周期维护和真实产品价值时仍有外部有效性限制。

## 提炼后的方法与 Nova 的关系

| 提炼内容 | 在 Nova 中如何落地 | 为何不照搬原结构 |
|---|---|---|
| 最小任务约定 | 日常共同原则先明确结果与验收，对话或已有任务承载本轮边界和未知 | 不要求每次先生成一套文档，也不依赖特定研发 Skill 触发 |
| 按不确定性选路径 | 共同原则决定何时先验证，手册按分支展开；复杂需求需要时再集中梳理 | 需求未定不能强行走设计到路线图的单向链 |
| 按影响面控制深度 | 复用现有共用约束和具体 Skill 合同 | 不建立第二套权限、生命周期或风险规则 |
| 可用小步与真实验收 | 复用现有 Operation、领域 Workflow 和已保存入口 | 方法选择不等于执行，Action 成功不等于功能闭环 |
| 事实与记忆分层 | 当前来源各归其主，短交接与稳定理由分开 | 既有体系已有所有者，不再添加万能记忆文件 |
| 分层上下文 | 所有 Nova 任务共用短原则，手册按需，研究材料仅审方法时读取 | 随包分发不等于宿主常驻，复杂需求 Skill 不承担整套方法 |
| 实测改进 | 在现有任务记录或本轮对话中比较历时、人工投入、质量与费用 | 不用代码量、主观感觉或案例倍数承诺提效 |

短的日常原则维护在[共用约束](../../../../Docs/Onboarding/DEVELOPMENT_CONSTRAINTS.md#日常研发的最小原则)，由所有 Nova 任务的[共同入口](../../../../Docs/START_HERE.md#日常研发的共同入口)路由；详细做法只维护在[方法手册](../../../../Docs/Onboarding/AI_DEVELOPMENT_WORKFLOW.md)。复杂需求 Skill 只集中处理方案比较、复杂变化和阶段依赖，已有[项目任务路由](../../nova-project-router/SKILL.md)继续寻找具体领域能力。它采用只读 Router 契约，避免把尚未确定的研发过程伪装成已冻结的 Operation DAG。上述共同入口以实际读取为生效前提，不声称宿主已自动常驻或强制注入这些内容。

## 仍需由真实使用回答的问题

需要继续观察：它是否减少返工、是否容易误触发小改长流程、探索是否真的产生了有用决策、所读上下文是否与任务相称、兼容与退出验收是否更完整，以及是否值得把少量入口提示常驻。

这些都属于待检验的效果，不写成已经取得的收益。试用发现具体问题时，优先修正相应分支；只有反复出现、已有正文无法有效防止的遗漏，才考虑增加共同入口内容。
